# apps/voter Implementation Plan (Plan 3a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A voter can sign in on a phone, rank candidates on an explicit ranked list with visible ordinals, submit, and be shown a receipt once — with a styling layer that can be upgraded later without editing a component.

**Architecture:** Preact + Vite + TypeScript, three screens and no router. `packages/styles` holds the design tokens both apps share. The ranked-ballot component is the only piece with real logic, and it is where the tests concentrate. One Playwright smoke test proves the session cookie actually travels, which jsdom cannot.

**Tech Stack:** Preact, Vite, TypeScript, Vitest + `@testing-library/preact` + jsdom, `@playwright/test` (e2e only).

**Spec:** `docs/superpowers/specs/2026-09-21-frontends-design.md` (§1 architecture, §2 styling, §3 API client, §4 the voter app, §7 testing). Parent spec: `docs/superpowers/specs/2026-09-16-election-code-rewrite-design.md` §1, §4.
**Handoff — READ §2 BEFORE TASK 1:** `docs/superpowers/HANDOFF.md`

**Plan 3a of two frontend plans.** The API is complete at 399 tests; nothing here changes it.

## Global Constraints

- **No `.tsx` file contains a `style` attribute or a utility class.** Semantic class names only. This is the single rule that makes the styling upgradable later (spec §2.2), and it is a success criterion.
- **Every interactive element gets `min-height: var(--touch)` (44px), and no input's font-size is below 16px.** iOS Safari zooms the viewport for a smaller input, which reads as a broken page. Most votes will be cast on a phone.
- **`credentials: 'include'` on every request.** Without it the session cookie is never sent and every call fails in a way that looks like CORS (spec §1).
- **Dependencies:** `preact` only, at runtime. Dev: `vite`, `typescript`, `vitest`, `@testing-library/preact`, `jsdom`. No router, no state library, no CSS framework, no `axios`.
- **`packages/core` is imported for `minimumPreferences` and `validateBallot`** so the client check and the server check are the same function, never two that can disagree.
- **The e2e suite is a separate npm script, not part of `npm test`.** It needs a downloaded browser binary; the default suite must never depend on one.
- TDD throughout: failing test, watch it fail, implement, commit.

### Divergence from spec §1, recorded deliberately

Spec §1 says "Preact (via React alias)". The alias exists so React-ecosystem packages work, and this
app has none — it uses `@testing-library/preact` directly. So the alias is **not** configured, which
removes a layer of indirection from the build. If a React-only package is ever needed, add
`resolve.alias: { react: 'preact/compat', 'react-dom': 'preact/compat' }` to `vite.config.ts`; three
lines, no other change.

### Task 2: The API client

**Files:**
- Create: `apps/voter/src/api.ts`
- Test: `apps/voter/tests/api.test.ts`

**Interfaces:**
- Produces: `ApiError` (with `status`, `code`, `message`); `getBatchBySlug`, `getElections`, `voterSignIn`, `submitBallot`, `getReceipt`, `voidReceipt`; `type PublicElection`, `type Batch`

**Five endpoints, not a generated client.** The voter app touches
`GET /api/batches/by-slug/:slug`, `GET /api/batches/:id/elections`,
`POST /api/batches/:id/voter/session`, `POST /api/batches/:id/elections/:eid/ballots` and
`GET|POST /api/receipts/:token[/void]`. A shared client with the admin app would couple them to buy
one function (spec §1.1).

**The error contract is the interesting part.** Every API failure is JSON (the API's `app.onError`
guarantees it), so `ApiError` always carries the server's `code` when there is one, and the screens
map `code` to a remedy rather than printing a message (spec §3).

```ts
const BASE = import.meta.env['VITE_API_BASE'] ?? 'http://localhost:8787'

/**
 * Every failure reaches a screen as one of these. `status` 0 means the request
 * never completed — a phone losing wifi — which the ballot screen must treat
 * differently from any HTTP status (see spec §4.4).
 */
export class ApiError extends Error {
  constructor(readonly status: number, readonly code: string | undefined, message: string) {
    super(message)
    this.name = 'ApiError'
  }
}

async function request<T>(path: string, init?: RequestInit): Promise<T> {
  let res: Response
  try {
    // credentials: 'include' is not optional. Without it the browser never
    // sends the session cookie and every authenticated call fails in a way
    // indistinguishable from a CORS misconfiguration (spec §1).
    res = await fetch(`${BASE}${path}`, { credentials: 'include', ...init })
  } catch {
    throw new ApiError(0, 'network', 'We could not reach the server.')
  }
  const body = await res.json().catch(() => undefined) as { error?: string; code?: string } | undefined
  if (!res.ok) throw new ApiError(res.status, body?.code, body?.error ?? 'Something went wrong.')
  return body as T
}

const postJson = (path: string, payload: unknown): RequestInit => ({
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify(payload),
})

export type Batch = { id: string; slug: string; name: string; branding: Branding }
export type Branding = { title: string; org_name: string; accent_color: string; logo_url: string }
export type PublicElection = {
  id: string
  name: string
  seats: number
  status: 'open' | 'closed'
  candidates: { id: string; name: string }[]
}

export const getBatchBySlug = (slug: string) => request<Batch>(`/api/batches/by-slug/${encodeURIComponent(slug)}`)
export const getElections = (batchId: string) => request<PublicElection[]>(`/api/batches/${batchId}/elections`)

export const voterSignIn = (batchId: string, usuId: string, surname: string) =>
  request<{ first_name: string }>(`/api/batches/${batchId}/voter/session`,
    postJson({ usu_id: usuId, surname }))

/** The usu_id is carried by the session cookie and never appears here (spec §5). */
export const submitBallot = (batchId: string, electionId: string, preferences: string[]) =>
  request<{ receipt_token: string }>(`/api/batches/${batchId}/elections/${electionId}/ballots`,
    postJson({ preferences }))

export const getReceipt = (token: string) =>
  request<{ status: 'recorded' | 'voided'; election_name: string }>(`/api/receipts/${encodeURIComponent(token)}`)

export const voidReceipt = (token: string) =>
  request<{ status: string }>(`/api/receipts/${encodeURIComponent(token)}/void`, { method: 'POST' })
```

### Task 3: The ranked ballot

The centrepiece. Read all of it before writing anything.

**Files:**
- Create: `apps/voter/src/components/RankedBallot.tsx`
- Modify: `apps/voter/src/app.css`
- Test: `apps/voter/tests/rankedBallot.test.tsx`

**Interfaces:**
- Consumes: `minimumPreferences` from `@election/core`
- Produces: `RankedBallot({ candidates, seats, onSubmit, submitting })`

**What the legacy app got wrong, and what this must therefore do.** `toggleRank` appended clicks to an
array: no ordinal was ever shown, and changing preference 2 meant unticking everything after it. So:

- **The ordinal is always visible** beside each ranked candidate.
- **Removing a preference renumbers the rest and discards nothing.**
- **Reordering is arrows, never drag.** Drag is fiddly with a thumb and needs a keyboard equivalent
  built anyway — which is arrows. The first item's `▲` and the last item's `▼` are **disabled, not
  hidden**, so the row does not reflow under a thumb already moving toward it.
- **Submit is disabled below the minimum**, with a live count in an `aria-live` region so a screen
  reader hears the gate rather than discovering a dead button.
- **The minimum comes from `minimumPreferences(seats, candidates.length)`** — the same function the
  API calls, so the two can never disagree about what a valid ballot is.

### Task 6: The Playwright smoke test

**Files:**
- Create: `e2e/package.json`, `e2e/playwright.config.ts`, `e2e/auth-smoke.spec.ts`, `e2e/README.md`
- Modify: root `package.json` (an `e2e` script, deliberately not part of `test`)

**Interfaces:**
- Produces: `npm run e2e`

**Its purpose is narrow and nothing else can serve it: proving the browser actually sends the session
cookie.** Spec §1's shared-apex precondition fails silently, presents identically to a CORS
misconfiguration, and its blast radius is an entire AGM. jsdom cannot see it, because jsdom is not a
cookie jar with a `SameSite` policy. This is not a general e2e suite — the API has 399 integration
tests and duplicating them through a browser would be slower and prove less.

**It is not part of `npm test`**, because it needs a downloaded browser binary and the default suite
must never depend on one.

import { test, expect } from '@playwright/test'

/**
 * Cookies are not port-scoped, so localhost:5173 and localhost:8787 share a
 * cookie jar and SameSite=Strict is satisfied — the registrable domain is

 * here but not on preview URLs, where the registrable domains differ and the
 * cookie is silently never sent.
 */
// These match e2e/fixture.sql exactly, which the config seeds with
// `wrangler d1 execute --local` before the browser starts. Deliberately NOT

const USU_ID = '2400001'
const SURNAME = 'Lovelace'
const CANDIDATE = 'Alex'

test('the session cookie travels, and a ballot can be cast', async ({ page }) => {

  await page.getByLabel(/usu id/i).fill(USU_ID)
  await page.getByLabel(/surname/i).fill(SURNAME)

  await page.getByRole('button', { name: `Add ${CANDIDATE}` }).click()
  await page.getByRole('button', { name: /submit/i }).click()

`e2e/playwright.config.ts` uses `webServer` to start both `wrangler dev` (port 8787) and the voter

`e2e/fixture.sql` seeds what the test needs — a batch with slug `e2e`, a roll row for Ada Lovelace
