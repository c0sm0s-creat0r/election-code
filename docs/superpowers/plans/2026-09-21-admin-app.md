# apps/admin Implementation Plan (Plan 3b)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The officer can run an AGM end to end — import the roll, open an election, watch turnout, close, read the round-by-round result, override a tie-break on the record, export — and a door volunteer can work a queue from a phone, including guests and members the export missed.

**Architecture:** React 19 + Vite + TypeScript, `react-router` for ~10 routes, and the door as a **lazy-loaded** route so a volunteer's phone never parses the officer bundle. Reuses `packages/styles` unchanged. Renders `@election/core`'s own types for the result, so a change to the counting library's output is a type error rather than a silently wrong table.

**Tech Stack:** React 19, react-router, Vite, TypeScript, Vitest + `@testing-library/react` + jsdom.

**Spec:** `docs/superpowers/specs/2026-09-21-frontends-design.md` (§0 guests and door additions, §2 styling, §3 API client, §5 the admin app, §7 testing). Parent spec: `docs/superpowers/specs/2026-09-16-election-code-rewrite-design.md` §3 (ties), §4 (lifecycle), §5, §6.
**Handoff — READ §2 BEFORE TASK 1:** `docs/superpowers/HANDOFF.md`

**Plan 3b of two frontend plans.** 3a is complete at 60 tests; `packages/styles` already exists and is not modified here. The API is complete at 399 tests and Plan 2d's guest and door-addition endpoints are live.

## Global Constraints

- **No `.tsx` file contains a `style` attribute or a utility class.** Semantic class names only (spec §2.2). Grep-checkable, and a success criterion.
- **No count, partial tally or per-candidate figure is reachable before an election is `closed`.** Turnout is three integers. An officer who can watch the result develop makes every other control decorative (spec §4).
- **A tie-break control is labelled from the tie's `kind`, never from an assumption.** `exclusion` → "who is excluded"; `election_order` → "who is elected first". A control saying "pick the winner" collects the opposite of the officer's intent on an exclusion tie and the result looks correct.
- **The two door additions are two buttons with different wording.** "Add guest" (cannot vote) and "Add member" (can vote). One catch-all button lets a volunteer grant a vote by accident (spec §0.2).
- **The roll is never written to browser storage.** Memory only. 1,300 names on a volunteer's personal device would sit outside the purge (spec §5.3, `LIMITATIONS.md` §10).
- **44px targets and a 16px input floor**, inherited from `packages/styles`. The door screen runs on a phone in a queue.
- **`credentials: 'include'` on every request.**
- **Dependencies:** `react`, `react-dom`, `react-router` at runtime. Dev: `vite`, `@vitejs/plugin-react`, `typescript`, `vitest`, `@testing-library/react`, `jsdom`. Nothing else.
- TDD throughout: failing test, watch it fail, implement, commit.

### Task 3: Elections — create, candidates, and the freeze at open

**Files:**
- Create: `apps/admin/src/screens/Elections.tsx`, `src/screens/ElectionDetail.tsx`
- Modify: `apps/admin/src/api.ts`, `src/app.css`
- Test: `apps/admin/tests/elections.test.tsx`

**Interfaces:**
- Consumes: `createElection`, `addCandidate`, `renameCandidate`, `removeCandidate`, `openElection`, `getTurnout`, `listElections`
- Produces: `Elections({ batchId })`, `ElectionDetail({ batchId, election, onChanged })`

**Two rules the UI must state, not merely enforce** (spec §4):

- **Candidates freeze at open.** The rule is stated *before* the officer opens the election — "once
  voting opens, candidates cannot be added, renamed or removed" — because the API's 409 afterwards is
  too late to be useful. The legacy app allowed adding a candidate mid-vote.
- **No tally while open.** The detail screen shows turnout only: `ballots_cast`,
  `voters_checked_in`, `eligible`, and `added_at_door` beside them. **No candidate names with numbers
  next to them, at any status before `closed`.**

**The officer needs to list their own drafts.** The public `GET /elections` returns only `open` and
`closed` (that is the legacy hole spec §6 closes), so this screen tracks the elections it created in
component state and merges them with the public list. No new API route: a public route whose body
depends on a cookie is a cache hazard, and inventing an officer listing is Plan 3b's to request, not
to assume.

### Task 4: The result, and the tie-break override

**Files:**
- Create: `apps/admin/src/screens/Result.tsx`, `src/components/RoundsTable.tsx`, `src/components/TieBreaks.tsx`
- Modify: `apps/admin/src/api.ts`, `src/app.css`
- Test: `apps/admin/tests/result.test.tsx`, `apps/admin/tests/tieBreaks.test.tsx`

**Interfaces:**
- Consumes: `getResult`, `overrideTieBreak`; `Round`, `RoundCount`, `TieBreakRecord`, `TieBreakKind` from `@election/core`
- Produces: `Result({ batchId, electionId })`, `RoundsTable({ rounds })`, `TieBreaks({ tieBreaks, onOverride })`

**The rounds table has to be worth printing.** IGM was chosen over WIGM precisely so a scrutineer can
check a round table by hand (spec §3), so: one row per candidate, one column per round, figures in
`--font-figures` and right-aligned with `font-variant-numeric: tabular-nums`, plus status per round,
the surplus and transfer value of each distribution, and the non-transferable total. Rendered from
`Round[]` as exported by `@election/core`, so a change to the count's output shape is a compile error.

**The tie-break control is labelled from `kind`.** This is the whole reason `winner_id` was renamed to
`resolved_id`:

| `kind` | label |
| --- | --- |
| `exclusion` | "Choose who is **excluded**" |
| `election_order` | "Choose who is **elected first**" |

A control reading "pick the winner" would collect the opposite of the officer's intent on an exclusion
tie, and the resulting document would look correct. **A test asserts the label derives from `kind`** —
a correctness test wearing a UI test's clothes.

**Lazy, so a volunteer's phone downloads the door chunk and not the officer bundle.** `React.lazy` plus

**Search matches surname, first name, `"first last"` or USU id.** A member handing over a card is

`localStorage.length === 0` after the roll loads, because "we would never do that" is not a control.

note and says plainly that a guest cannot vote; "Add member" takes a USU id and a name and is for
someone the export missed. A 409 `already_on_roll` tells the volunteer to search instead.

## Success criteria for Plan 3b

- `npm run -w @election/admin test` and `typecheck` pass; dependencies are exactly those listed.
- **No `.tsx` file contains a `style` attribute or a utility class.**
- **No count, tally or per-candidate figure is reachable in the app before an election is `closed`** — asserted by rendering an open election and checking the text.
- Candidate controls are **absent**, not disabled, once an election is open, and the freeze rule is stated before opening.
- A tie-break control's wording derives from `kind`, asserted for both kinds.
- An override requires a reason and warns that the previous result is kept.
- The door search matches surname, first name and **USU id**, filters with no network request, and writes nothing to `localStorage` or `sessionStorage`.
- "Add guest" and "Add member" are separate buttons, and the guest form states that a guest cannot vote.
- The door route is a separate chunk in `vite build` output.
